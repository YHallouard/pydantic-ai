# Plan: `Loop` capability — keep running until a stop criteria is met

> Working document. Not intended to be merged: this file exists so we can align on the design
> (and ideally get maintainer input) before writing any implementation code.

## 1. Problem

Today an agent run ends as soon as the model produces a final output (text, or an output tool
call). There is no supported way to say *"this isn't done yet — keep going until X holds"*.

Users who want that pattern have to leave the framework and write their own outer loop:

```python
messages = None
for _ in range(10):
    result = await agent.run(prompt, message_history=messages)
    if is_good_enough(result.output):
        break
    messages = result.all_messages()
    prompt = 'Not there yet: ...'
```

This works, but it loses everything the run owns: a single `run_id`/conversation, one usage
total, one span tree, one event stream, streaming, and durable execution. Every user
re-implements bounding, feedback formatting, and history plumbing slightly differently.

The pattern itself is well-established: Claude Code's `/loop`, verification loops in coding
agents (test → fix → repeat), reflexion/self-critique loops, and "iterate until the reviewer is
happy" workflows.

### Prior art in the ecosystem

- [`pydantic/pydantic-ai-harness#79`](https://github.com/pydantic/pydantic-ai-harness/issues/79)
  — "Verification Loop capability (test-lint-build → fix → repeat)". Proposes a
  `VerificationLoop(AbstractCapability)` that intercepts the agent's attempt to stop, checks
  success criteria, and re-feeds context. Currently blocked on harness-side dependencies, and
  scoped to *shell verification commands* specifically.
- Claude Code's `/loop`: two modes — a fixed interval, and a **dynamic** mode where the model
  itself decides when to stop.

**Observation:** harness#79 is the *narrow, opinionated* version (run shell commands, parse
failures). The general primitive underneath it — *"don't end the run until a criteria is
satisfied, and feed the failure back"* — belongs in `pydantic-ai-slim` as a capability, and
harness#79 becomes a thin `Loop(stop_criteria=run_verification_commands)` on top of it.
That framing matches the repo's stated preference for strong primitives over narrow solutions.

**Open question (blocking, for maintainers):** is this primitive wanted in core
`pydantic-ai-slim`, or should it live in the harness / a third-party capability package? No
core issue exists yet. This plan should become a proposal comment on a new core issue before
implementation starts.

## 2. Proposed API

A new capability in `pydantic_ai_slim/pydantic_ai/capabilities/loop.py`:

```python
from pydantic_ai import Agent
from pydantic_ai.capabilities import Loop

agent = Agent(
    'anthropic:claude-opus-4-6',
    capabilities=[
        Loop(
            stop_criteria=lambda ctx, output: 'All tests pass' in output,
            max_iterations=5,
        )
    ],
)
```

### 2.1 Forms of stop criteria

```python
LoopStopCriteria: TypeAlias = (
    StopCriteriaFunc[AgentDepsT]  # Python predicate
    | str                          # natural-language criteria, judged by a model
    | Literal['auto']              # criteria derived by the model from the task
)
```

| Form | Meaning |
|---|---|
| Callable `(ctx, output) -> bool \| str \| None` | Full control. Sync or async. |
| `str` | Natural-language criteria; an LLM judge decides each iteration and supplies feedback. |
| `'auto'` | The model writes the success criteria itself, **once**, from the task at run start; the same judge then evaluates against those criteria each iteration. |

The `'auto'` form is the "auto-generated by the LLM on demand" requirement. Deriving the
criteria **once up front** (rather than re-asking "are you done?" every turn) matters: it
gives a stable target the model can't quietly relax, and it makes the criteria inspectable —
they are emitted as an event and stored on the run so users can see what the agent committed to.

### 2.2 Callable return value

| Return | Meaning |
|---|---|
| `True` | Criteria met → the run ends with this output. |
| `False` / `None` | Not met → continue, using the default continuation prompt. |
| `str` | Not met → continue, and use the string as the feedback message. |

**Decision point.** `True` = stop while a truthy `str` = continue is a readability trap.
Alternative: a single explicit return type, `LoopDecision(stop=..., feedback=...)`, with
`bool`/`str` accepted as shorthand. Leaning towards accepting both and normalizing internally;
the shorthand keeps the 90% case a one-liner, which matters for a capability whose whole
selling point is replacing a `for` loop.

### 2.3 Full field list (first cut)

| Field | Type | Default | Purpose |
|---|---|---|---|
| `stop_criteria` | `LoopStopCriteria` | `'auto'` | See above. |
| `max_iterations` | `int` | `10` | Hard bound. Counts *completed* iterations. |
| `on_max_iterations` | `Literal['stop', 'error']` | `'stop'` | Return last output, or raise. |
| `continuation` | `str \| Callable` | built-in text | Message sent back when the criteria isn't met. |
| `model` | `Model \| KnownModelName \| None` | `None` | Judge model for `str`/`'auto'`; defaults to the run's model. |
| `id` / `description` | | | Standard capability fields. |

## 3. Mechanism

Direct precedent already exists in this repo:
`capabilities/_pending_messages.py::PendingMessageDrainCapability.after_node_run` intercepts an
`End` and returns a `ModelRequestNode` instead, redirecting the graph back into another turn.
`Loop` uses the same hook.

```
after_node_run(ctx, node, result)
  ├─ result is not End                        → pass through
  ├─ iteration count >= max_iterations         → pass through (or raise)
  ├─ evaluate stop criteria against result.data.output
  │    ├─ stop  → pass the End through unchanged
  │    └─ continue → append feedback ModelRequest, return ModelRequestNode(request=...)
```

Why `after_node_run` and not `wrap_run`:

- Everything stays inside **one** agent run — one `run_id`, one usage total, one span tree,
  one event stream, and it works identically under `run`, `run_stream`, `iter`, and durable
  execution. Re-driving the run from `wrap_run` would produce N nested runs.
- History is already consistent at that point: `CallToolsNode._handle_final_result` appends
  tool return parts to `message_history` *before* returning `End`, so redirecting never
  leaves a dangling tool call.
- The `End[FinalResult]` carries the **validated, typed output** of the iteration, so the
  stop criteria sees `output: OutputDataT`, not raw text. This is the key ergonomic win over a
  user-written outer loop, which only sees text unless it re-validates.

### Ordering

`CapabilityOrdering` — `Loop` must sit **inside** `PendingMessageDrainCapability` (which is
`position='outermost'`). Since `after_node_run` hooks run in reverse order, `Loop` sees the
`End` first and redirects; the drain capability then sees a `ModelRequestNode` and no-ops. That
falls out of the existing `outermost` placement, but needs an explicit test.

### `run_stream`

`wrap_node_run` is documented as not firing for the final `ModelRequestNode` under
`run_stream()`. The graph still reaches `End` through `SetFinalResult`, which *is* a node, so
`after_node_run` should still fire. **To verify before implementation** — if it doesn't,
`Loop` under `run_stream` is either broken or needs a second hook, and that changes the design.

## 4. Things that need answering before writing code

1. **Core or harness?** (blocking — see §1)
2. **Where does the loop state live?** Iteration count, derived criteria, and per-iteration
   outputs are per-run state. `for_run()` returning a fresh instance is the established pattern
   for per-run isolation; confirm it composes with durable execution replay (a Temporal replay
   must not re-derive `'auto'` criteria non-deterministically — the derivation is a model call
   and must be recorded).
3. **Is the intermediate output visible?** Each iteration produces a validated output that is
   then discarded. Should `AgentRunResult` expose the sequence (`result.loop_outputs`)? Adding
   a field to `AgentRunResult` for one capability is a smell; an event
   (`LoopIterationEvent`) on the event stream is likely the right surface instead.
4. **Interaction with `UsageLimits.request_limit` (default `50`).** A long loop will hit it and
   raise. Document it; do not special-case it.
5. **Should `Loop` also expose a model-facing `stop` tool?** ("model declares it's done"). This
   is a third stop mode and arguably belongs to the same capability, but it changes the tool
   surface. Leaning: **out of scope for v1**, revisit after the hook-based version lands.
6. **Spec serializability.** `Loop(stop_criteria='...')` and `Loop(stop_criteria='auto')` are
   YAML-representable; the callable form is not. Check how `WebSearch` handles the same
   split (it has a serialization name but accepts callables) and follow that precedent.
7. **Naming.** `Loop` vs `Iterate` vs `UntilCriteriaMet`. `Loop` is short and matches the
   Claude Code vocabulary, but it is a *very* generic name to claim in
   `pydantic_ai.capabilities`.

## 5. Implementation checklist (once the design is agreed)

- [ ] `pydantic_ai_slim/pydantic_ai/capabilities/loop.py` — `Loop`, `LoopDecision`,
      `LoopStopCriteria`, `StopCriteriaFunc`
- [ ] Judge for `str` / `'auto'` criteria — a small internal sub-agent with a structured output
      (`met: bool`, `feedback: str`), reusing the run's model unless `model=` is set
- [ ] Export from `capabilities/__init__.py`; register in `CAPABILITY_TYPES` if spec-constructible
- [ ] `LoopIterationEvent` (if §4.3 lands that way) in `messages.py` + UI adapter round-tripping
- [ ] Tests in `tests/capabilities/test_loop.py`: callable/`str`/`'auto'` criteria; stop on
      first iteration; `max_iterations` under both `on_max_iterations` values; typed
      `output_type` across iterations; tool-output runs (no dangling tool calls); `run_stream`
      and `iter`; composition with `PendingMessageDrainCapability` and compaction; usage
      accumulation across iterations
- [ ] `docs/capabilities/loop.md` + `mkdocs.yml` nav + row in `docs/capabilities/overview.md`
- [ ] Update the `building-pydantic-ai-agents` skill if the loop becomes a recommended pattern

## 6. Explicitly out of scope

- Interval / time-based looping (Claude Code's `/loop 5m`) — that is a scheduler concern, not
  an agent-run concern.
- Shell verification commands (harness#79) — builds *on top of* this primitive, stays in the
  harness.
- Multi-agent / reviewer-agent loops — expressible as a callable stop criteria that runs
  another agent; no dedicated API.
